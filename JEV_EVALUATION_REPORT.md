## Executive Summary

This evaluation supports Jev as a supplemental-reading ranker for expensive
Codex review work. It does not support using Jev to select the mandatory audit
packet, declare a packet complete, waive a gate, or replace an independent
reviewer. The useful recommendation is to rank optional background for a
concrete review question, retain the required cross-layer packet unchanged,
make every omitted source available for follow-up, and use the repair diff plus
affected evidence for repair reviews.

The original easy evaluation found Jev at 8/8 top-1 localization versus 5/8
for its IDF-weighted lexical baseline, and 8/8 versus 6/8 at top three. Its
four missing-source probes returned `unknown`, and its four simple injected-
instruction probes selected the correct candidate. The stronger rigorous run
found Jev recovered all required evidence at top four in 5/8 answerable cases
in order A and 6/8 in order B, versus 3/8 for BM25. That is promising ranking
evidence, not safe packet-completeness evidence.

The rigorous packet-choice result matched the frozen preset label in 7/10
cases. The disagreements must remain visible: q05's required-label set was
overstrict because `s04` plus `s16` already answered the question; q06 and q07
were actual false escalations according to the independent Sol review. The
raw 7/10 coverage-match result is preserved and was not retuned.

There is no proven unsafe Jev audit verdict in this evidence. Incomplete
retrieval, order sensitivity, and false escalation do limit operational use.
The 81.6% figure is a character-count reduction for one supplemental-packet
calculation, not measured Codex Pro savings. If one audit needs all eight
topics, deduplication can make the apparent savings zero.

## Purpose And Non-Goals

The purpose was to test whether a bounded Jev pass can reduce expensive-agent
context and rereading while preserving audit safety. The scarce resource is
Codex Pro usage, not Jev inference cost. This was generated from saved
artifacts; no new API request was made while writing this report.

Jev returns typed `Score` and `Choice` judgments, not prose explanations. Every
explanation below is explicitly this report's analysis of the cited evidence,
not a prose answer generated by Jev. Jev confidence is distribution
concentration, not proof or permission to act.

The evaluation does not measure compiler correctness, reviewer correctness,
calibration, sustained latency, billing, actual Codex usage savings, or the
security of a general retrieval system. It also does not alter compiler,
runtime, schema, test, milestone, or release authority.

## Methods

### Original Evaluation

The initial batch scored eight candidates for each of eight lookup questions
and classified six contract claims. The labels were lead-curated before the
requests and were not independent held-out human gold. Jev used a 0-3
directness score. The comparison was an IDF-weighted query-term presence
baseline, not BM25. The eight stress cases reused selected questions with the
expected source removed or a misleading instruction appended to a wrong
candidate.

The context-budget calculation reused existing answers without extra Jev calls
or audit agents. It compared 507,544 full supplemental characters with
130,563 selected characters, a 74.3% proxy reduction, while retaining the
expected source for all eight separate questions. This is not measured Pro
savings. The selected source unions are not a safe all-topic packet: when one
audit needs all eight topics, deduplication removes the apparent saving.

### Rigorous Evaluation

The rigorous benchmark froze 24 excerpts across eight files, 32,506 source
characters excluding terminal newlines, and ten questions. Eight questions
were answerable and two deliberately lacked the requested final audit or timing
records. The required source labels were frozen before inference. They are
independent Sol-authored labels, not human gold truth.

Each question was ranked twice with shuffled candidate order and reassigned
opaque IDs. The baseline was BM25 with `k1=1.2`, `b=0.75`, and lowercase
alphanumeric tokenization. Both methods saw the same candidate text. There was
no prompt tuning after results. Requests used a 30-second timeout and no
retries. The 81.6% rigorous figure compares 325,060 all-background characters
with 59,760 first-run top-four packet characters; mandatory diff, contracts,
tests, follow-up reads, and reviewer reasoning are outside the calculation.

## Per-Case Analysis

This section states the substantive answer a reviewer should verify. It is
Luna's analysis of the source IDs, not a prose response from Jev.

### q01: New Versus Legacy Process Launch

**Answer:** The launches are not equivalent. The new API requires an absolute,
NUL-free executable path and `execve`, with dedicated process-group and
direct-child cleanup ownership; legacy `run_process` retains PATH lookup and
does not own a process group.
**Explanation:** `s01` and `s02` define the distinct public launch and cleanup
contracts, `s03` defines the owned lifecycle, and `s18` shows the legacy wait
path. A thin wrapper would erase executable-resolution and cleanup boundaries.

### q02: Termination, Waiting, And Ownership

**Answer:** After successful termination on an active child, a repeat
termination is allowed on the cached ready state, and `process_wait` consumes
the process handle and returns the cached outcome.
**Explanation:** The checker distinguishes consuming wait from mutating
termination and tracks moved state; the runtime's `process_wait` drops the
handle after extracting the outcome, while `process_terminate` accepts a ready
state. `s03`, `s17`, and `s20` must be read together.

### q03: Race Precedence

**Answer:** A fresh natural-exit observation wins. `cancelled` is set only when
the child was not observed exited and cancellation was requested at the action;
`timed_out` is set only when it was not observed exited and the deadline had
expired.
**Explanation:** `s03` gives the contract-level precedence and `s19` shows
the runtime condition `!exited && expired/cancel`. A deadline or cancellation
does not retroactively relabel an already observed natural completion.
The flags classify the action taken, not proof that it caused the child's exit.

### q04: Recursive Cleanup Authority

**Answer:** A function acquires cleanup-related IO/process authority when a
checked owned process type appears directly or nested through recognized
containers/product fields. Names, fields, and `ref`/`mutref` views do not create
new ownership authority. The authority is seeded before the transitive IO
fixed point.
**Explanation:** `s04` states the canonical checked-type closure and seed
contract; `s14` excludes borrowed/name/field expressions; `s13` performs the
recursive owned-type closure; and `s12` is the authority-seeding path.

### q05: Qualified User Function Versus Builtin

**Answer:** Evidence must use the checked target's origin and kind, not the
spelling `process_wait`; a qualified user function with that name remains a
user function. If a source call does not join to exactly one checked target,
the evidence path emits `NQ-INTERNAL-012` and fails closed.
**Explanation:** `s04` defines the checked-origin boundary, `s15` defines
user-versus-builtin classification, and `s16` joins call sites by checked
ranges and rejects zero or ambiguous matches.

### q06: Cache Reuse Authority

**Answer:** No. An existing executable and execute bit are insufficient. Reuse
requires the linked input, seed manifest and executable, emitted C and
executable, compiler identity/target/version, flags, derivation receipt, and
cache identities to agree.
**Explanation:** `s06` makes current verification a provenance decision and
`s21` checks the complete identity chain before accepting the stage1 cache.
The top-two packet is substantively sufficient even though its Jev packet
choice escalated; that is the recorded false-insufficient case.

### q07: Stale Or Skipped Proof Artifacts

**Answer:** Active proof evidence must report skipped or unreached artifacts as
null/unperformed rather than reuse stale files. Copied-selfhost parity requires
stage1 emit, C compile, stage2 run, stage2 emit, normalized structural compare,
and matching smoke behavior on the same copied workspace.
**Explanation:** `s08` defines null semantics for skipped artifacts and
`s11` gives the full copied-selfhost chain. The top-two packet contains both,
so Jev's request for more evidence is a false escalation, not a safety proof.

### q08: Current-State Attestation

**Answer:** `milestone-attestation verify` reconstructs the expected attestation
from the current candidate, toolchain, cache, proof, and release identities and
compares the stored record to that reconstruction. It does not accept file
existence as freshness. The stated remaining threat is a malicious owner who
rewrites every trust root.
